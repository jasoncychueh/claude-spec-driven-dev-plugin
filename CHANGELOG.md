# Changelog

Version history and decision rationale are collected here. The skill / reference / agent docs describe only the **current rules + technical rationale**; they do not narrate version evolution — consistent with this plugin's own principle that "formal docs describe the world after the decisions are made".

## 1.22.0 (2026-08-30)

1.21.0 shipped a resume-count checkpoint and it worked, in the narrow sense: within a day the resume long tail was gone — max **8** resumes on any session, median 3, nothing past the soft mark, against 105 and 119 the week before. The measurement that followed showed the axis was wrong anyway, and that a premise this changelog recorded as settled was false.

**What the data said.** Per-day totals were down, but the peak 5-hour window held **53%** of the day's weighted usage — the highest concentration of the week — which is what a rolling limit actually sees. Cost had not left; it had moved. `spec-implementer` alone accounted for **56%** of subagent spend, at a median of **727 requests** and **589K** peak context per session, with dispatches running to **285 turns**. Executors reached a median peak of **461K** and a maximum of **997K**, and the subagent transcripts carry **151 `compact_boundary` markers**: the harness had been autocompacting executors at ~930K all along, some of them three times over.

- **The axis was wrong: retire on context size, not on resume count.** Cost and defocus track how large a session has grown, not how often it was resumed — and the two now point in opposite directions. Smaller bounded dispatches continued by resume are the prescribed shape, so resume counts rise *precisely when the discipline is working*; a hook complaining at #15 would have been complaining about the behaviour the skill asks for, and would have taught the main agent to ignore it. The ceiling is **400K**, checked at the moment of resume, with a 300K notice one dispatch ahead.
- **Retirement, not compaction — and the ordering is the whole mechanism.** 400K sits far below the ~930K the harness compacts at, so a session retired on time is never compacted at all. That matters because this workflow keeps the executor's basis **on disk**: a fresh spawn re-reads the authoritative design.md, tasks.md and review-log §1, while a compacted session keeps a paraphrase of them and cannot tell what it lost. The user's own framing settled it — *"don't worry about losing context, we have complete documentation"* is an argument **for** retire-and-respawn, not for compaction.
- **Corrects 1.21.0's "Rejected: autocompact for subagents".** That entry rejected the idea on the reasoning that compacting an executor's working basis trades visible defocus for invisible spec drift. The reasoning stands; its **premise did not**. It assumed compaction was something we were choosing to avoid, when in fact it had already happened 151 times. The drift it warned about was not hypothetical — it was the status quo, and the status quo was the worst of both worlds: executors burned the full ~930K ramp *and then* continued as lossy summaries of themselves.
- **The 1M / 400K split is not a knob, so the ceiling is enforced by the two levers that are.** `--autocompact` is per-session and shared by the main agent and its subagents; there is no per-agent field and no subagent-scoped setting (`subagentPromptCacheTtl` exists, no autocompact analogue). Setting it globally to 400k would also be *actively harmful*: the main agent already averages ~401K per request, so it would sit permanently on the compaction boundary. Instead: **`maxTurns` bounds one dispatch** — invisible to the hook, since no `SendMessage` happens mid-dispatch — and **the hook bounds accumulation across dispatches**, invisible to `maxTurns`, whose budget resets on every resume. Neither covers the other; that is why both ship.
- **`maxTurns` on every agent, calibrated from measured per-dispatch turn counts.** Verified live before being relied on: a dispatch is cut at the ceiling and returned marked **partial** with a continue hint, a **turn is one assistant message carrying a tool call** (thinking and text cost nothing), and the budget **resets on every resume** — so "smaller chunks, same agent" is the shape the harness rewards. `spec-implementer` 45 and `spec-tester` 20 sit at their medians, checkpointing ~half of all dispatches; `implementation-reviewer` 40, `design-reviewer` 30 and `spec-author` 25 cut the top ~20% of outliers. Simulated against three days of real dispatches the whole set costs **+420 round trips ≈ 0.5%** of weighted usage. What it buys is not context (a single dispatch adds only ~20-64K) but **arbitration**: half of implementer dispatches now surface real work in progress instead of returning after 285 unwatched turns.
- **An already-compacted session is the clearest retire case, and token size hides it.** After the harness compacts an executor its next usage record starts from the summary at ~100K, so a session that already blew through the ceiling would read as small and pass silently forever — inverting the entire point, since it is the one session guaranteed to be working from a paraphrase of its basis rather than the basis. The hook therefore looks for a `compact_boundary` marker in the transcript tail and calls for retirement on that alone, ignoring the token count. Verified against a real compacted subagent transcript.
- **A round is one completed issue list, not one dispatch.** `maxTurns` introduces exactly one failure mode — a truncated dispatch read as a finished unit of work — and the fix is to define the unit properly rather than to loosen the ceiling around it. A partial return means the round is unfinished: resume it, don't advance the round number, write no §1 audit row, and never read it as `0 issues`, since an incomplete sweep that has not yet found a problem looks exactly like a clean one. Convergence may only be declared from a round the reviewer itself concluded.
- **`effort: medium` on the sonnet executors** (`spec-implementer`, `spec-tester`, `spec-verifier`) — they execute against a written design rather than making open-ended calls. Expectations set honestly: output was ~2% of weighted usage even at 5× weighting, so this is a latency lever, not a usage one.
- **Fan out wide, in one message.** The parallel-group mechanism was already specified and measurably unused — real cycles ran phase-by-phase and serial. Stated with its trade rather than as a free win: compressing the same work into fewer wall-clock hours draws harder on a rolling usage window, which is the concentration the measurements above found.

## 1.21.0 (2026-08-27)

Executor sessions run far too long. Reported from use — subagents on multi-hour tasks accumulate enormous context, and past a point a larger context is not better: attention defocuses, and a cheaper-tier executor loses the thread of the task in front of it.

The transcripts settle how bad it is. Counting `SendMessage` calls per subagent id across real sessions: the median executor takes **~10-15 resumes**, and the tail reaches **119 and 105 resumes on a single subagent**. By then the session's context is mostly a record of its own earlier reasoning rather than the work at hand — which the protocol had already conceded elsewhere without generalizing, since the convergence fuse spawns a *fresh* reviewer at Round 5 for exactly that reason.

- **Retire sessions; don't run them indefinitely.** 1.20.2 made resume justify itself per dispatch (name the asset). This adds the standing test the per-call one couldn't express: re-check the asset deliberately around **15 rounds**, and by **25** retire the session unless the asset is still nameable and genuinely large. A fresh spawn takes the current artifact state plus review-log §1 — the same rebuild the resume-failure fallback already prescribes, so nothing new had to be invented to make retirement cheap.
- **Mechanical work wants a clean executor, not a warm one.** Applying a stated fix to named files carries no tacit knowledge by definition — there is nothing to remember, and a long history is pure distraction. The named defaults ("resume the session that owns these files") assume the fix needs to know *why the code is shaped this way*; when it plainly doesn't, the assumption doesn't hold.
- **A `SendMessage` checkpoint hook, because the main agent forgets.** Every rule here competes with "resume, don't respawn" and with a fresh spawn reading as broken discipline, so prose alone loses over a long session — the same lesson as 1.18.2 and 1.20.1. The hook counts prior `SendMessage` calls sharing the same `to` in the transcript (a subagent is resumed by messaging it, so the round count is free — no state file) and injects a note at **#15** and again from **#25**. It emits **no `permissionDecision` at all** — it cannot block, prompt, or alter a call. That is the design, not caution: whether this session holds tacit knowledge a fresh spawn would lose is visible only to the main agent, so a permission prompt would put the question to the user, who sees a hex id and a number and has no basis to answer — a ceremony to click through, which is the shape of thing this skill removes elsewhere (1.17.0's manufactured challenges) rather than adds. What the main agent lacks is not judgment but the count: its context holds no record of how many times it has resumed a session, which is part of why the reflex runs unchecked. So the hook supplies the fact, the rule supplies the criterion, and the main agent decides. If it resumes anyway at #25, that is either a reason the hook cannot see or a misjudgment a blocking gate would not have improved. Fail-open on every uncertainty; filters `isSidechain` so a subagent's own dispatches never count. Reviewer sessions are not exempt (a long reviewer is precisely what the fuse treats as suspect, and its corpus re-reads cheaply from disk) and the threshold sits far above a normal review loop.
- **Rejected: autocompact for subagents.** The obvious reading of "too much context" is to compact earlier, and `claude --autocompact 200k` exists — but it is session-wide (one process, main agent and subagents together), so it cannot target executors, and aiming it at them would be *harmful*: the main agent compacts conversation history, which summarizes acceptably, while a subagent's context is its **working basis** — the design section, the file list, the issue text. Compacting that yields an executor that has forgotten half its specification and is still writing code, trading visible defocus for invisible spec drift. The problem is that sessions live too long, not that their context is stored inefficiently.

## 1.20.2 (2026-08-27)

The main agent resumes existing subagent sessions on reflex, rather than deciding per dispatch whether that session's history actually helps. Same root as 1.20.1's stalled executors: those had been resumed continuously across a whole cycle, which is also why their prompts were stale.

The rules already in place looked airtight — resume is scoped to one loop, cross-spec resumes are never correct — but every one of them draws its boundary at the **cycle**, and the failure happens *inside* a cycle where all of them are silent. Worse, the test they offered ("does this dispatch continue the work this session already holds?") is answered *yes* by almost anything in the same feature, so the reflex passes the check it was supposed to face. And the surrounding language pushes the same way: sessions are called "persistent", the rule is phrased "resume, don't respawn", and a fresh spawn reads as breaking discipline rather than as the neutral default it should be.

- **Name the asset, or spawn fresh.** Resume must now be justified in one clause by what that session's context gives *this* dispatch, and exactly two things qualify: **tacit knowledge that exists nowhere on disk** (why the code is shaped this way, what was tried and rejected, what the brief meant), or **a corpus already read that this dispatch needs again** (the reviewer's artifact + issue history across rounds, where re-acquisition costs more than staleness risks). Can't name one → fresh spawn. What explicitly doesn't qualify is the reflex's actual reasoning: "same feature", "still this cycle", "already warmed up" — that is topic continuity, and a fresh agent reading the same files on disk is equivalent, cheaper in context, and unbiased.
- **The named defaults are instances, not exceptions.** "Resume the group's owning session", "resume its Stage 1 session" — each passes the test on tacit knowledge, and is stated that way so the rule reads as one principle rather than a rule plus a pile of carve-outs.
- **A new phase's groups are fresh spawns.** Grouping is recomputed per phase, so a new group is new work over files the old session never read; resuming inherits an unrelated reading list, and its tacit knowledge is about other code. Previously unstated, and the most likely place for the reflex to bite inside a cycle.
- **Say that the asset decays.** The protocol already acts on this — the convergence fuse spawns a *fresh* reviewer at Round 5 precisely because a long-running session anchors on its own earlier conclusions. That was written as a Round-5 special case; it is the general property, and now says so: the longer a session runs, the more its context records its own reasoning rather than the world.

## 1.20.1 (2026-08-14)

Field report from a session running the plugin: `spec-implementer` / `spec-tester` backgrounded long runs (`dotnet test`, `build.ps1`, a Host launch) and ended their turns **at least six times**, each waiting for a completion notification that cannot reach a subagent. Every one cost 5–15 minutes plus a manual main-agent nudge, and in a serialized multi-executor build it stalls the whole line. (That session's executors were spawned before 1.18.1 and resumed throughout, so their prompts predated the rule — but the transcripts still exposed two real gaps in it.)

- **Name the competing guidance and override it.** One executor cited *"the no-polling discipline"* while waiting, and that discipline is real: the harness tells every agent a backgrounded task will notify on completion and that polling is wasteful. It is correct **for the main agent**, which genuinely does get woken; it reaches a subagent as boilerplate that is false about it — the rule and its mechanism come as a pair, and the subagent inherited only the rule. 1.18.1 prohibited background work without ever mentioning it, leaving the model to weigh an explicit, mechanism-bearing instruction against what reads as a preference. This is 1.18.2's shape exactly, so it gets 1.18.2's fix: `spec-implementer`, `spec-tester`, and `spec-author` now name that guidance, state it is addressed to the main agent, and override it — plus the sentence that precedes the failure (*"I'll wait for the notification before proceeding"*) as an explicit stop signal, since the model can catch itself composing it.
- **Cover the already-backgrounded case, which 1.18.1 left with no exit.** The old rule only said *don't background*; an executor that already had a task running — started before it read the rule, or handed to it — had a prohibition and no procedure, and waiting was the only move the text allowed. Now: poll it to completion **inside the turn**, use a wait-for-condition tool if one is offered, or abandon it and re-run in the foreground with the timeout at maximum. Waiting *within* a turn costs time; ending the turn costs the dispatch.
- **The main agent gets the other half.** Every executor dispatch prompt carries the one-line rule — deliberately redundant with the agent definitions, because this failure stalls a whole line rather than degrading one result, and a dispatch prompt reaches an executor whose definition doesn't. And an executor report saying "waiting for the background task" is named as a **stalled dispatch, not a status update**: resume it immediately rather than waiting for a follow-up that will never come.
- **Also fixed, from the same report**: a list handed to an executor is often worked one item deep and then reported on, the rest read as context — turning a batch into an accidental stepwise dispatch at one round trip per item. Both the dispatch guidance and `spec-implementer` now say the list is the turn's work: run it to exhaustion, report when it's done **or when you hit a blocker**. That last clause is load-bearing — without it "don't stop" collides with stop-instead-of-thrash and a blocked executor grinds instead of reporting.

## 1.20.0 (2026-08-14)

Steering was silting up with operating knowledge. Observed in use: agents promote the traps they tripped over during the cycle — "refresh the token before calling X or you get a 401" — and steering drifts from a set of guardrails toward an operations manual, which is precisely how it rots (it is read as the project's standing intent, so every operating detail added to it buries the clauses that actually constrain design).

The existing bar didn't stop it, and the reason is instructive: **every threshold in the skill measured *breadth*.** Three conditions (spans the whole project / omitting it will cause trouble / not already recorded) plus four exclusions (spec-specific, implementation detail, project-memory fact, merely tidier) — and a trap hit three times during a cycle **passes all of them honestly**. It really does span features, it really will recur, it really isn't written down. The agent's reasoning was sound; the rule was asking the wrong question. What was wrong was never the scope, it was the **kind**.

- **A type test that runs before the breadth bar.** Steering records the project's **decisions** — what we chose, what we always do, what we never do; naming a concrete tool still counts, which is what tech.md is for. CLAUDE.md records **how to operate this repository** — commands, environment traps, required sequencing. The probe: **can you explain why the rule exists without recounting an incident?** A decision stands on its own; operating knowledge without its war story is an unexplained step. So "we hit this three times" marks CLAUDE.md material regardless of breadth — the recurrence is real, it just makes it *important operating knowledge* rather than a principle.
- **A rejected probe worth recording.** The first draft asked "would this survive swapping the tech stack?" — and it would have shipped a contradiction: tech.md exists to record the stack, so pytest, the architecture pattern, and every framework choice all fail that probe and would have been misrouted to CLAUDE.md by a reviewer following instructions faithfully. It confused breadth with kind, the same error the release exists to fix. The incident probe is the one that actually cuts along the decision/knowledge seam.
- **The findings get a home, not just a prohibition.** A rule that only forbids leaves the agent choosing between losing a genuine recurring trap and misfiling it — and it will misfile it, every time. So `[claude-md]` is a first-class outcome: every candidate carries a `[steering]` or `[claude-md]` tag in the same `📌 Steering Candidates` section (tag required, part of the output format rather than prose), the main agent **routes by tag and re-judges rather than trusting it**, and both destinations are written only after the user confirms. No agent edits CLAUDE.md on its own. Review-log §5 records both, so the promotion channel keeps one audit trail instead of one visible record and one invisible one.
- **Threaded through every place that stated the old bar**: `review-protocol.md` (definition, output format, main-agent routing), `steering-guide.md`'s refinement principle, SKILL.md's Steering Evolution Mechanism + Core Principle #7, both reviewers, `spec-implementer` (flagged as the agent most likely to confuse the two, since a trap it hit repeatedly *feels* like a project rule), `checklists.md` in both review sections, and `review-log-guide.md` §5.

## 1.19.1 (2026-08-11)

Close the one gap 1.19.0's design left open: **`spec-author` writes both the design and the test cases, so a misread requirement is implemented *and* verified.** The design implements the misreading, the case certifies it, the test goes green — and the feature ships *certified wrong*, which is worse than shipping untested, because the suite now supplies evidence for the mistake.

Checked against 1.19.0's actual §6 aspects, this passes every one of them. Requirement "an expired claim is released automatically", misread as "released when the session ends": the case names a real requirement (anchor legality ✓), that requirement has a case (coverage ✓), "released when the session ends" is a genuinely observable outcome and not a mechanism ✓, the level fits ✓. Seven checks, none of which look at whether the case says what the *requirement* says.

- **A `Requirement fidelity` check, in `design-reviewer` §6 and the matching checklist.** For every `behavior` case, read the **requirement's own text** and apply one probe: **would this case still be correct if the design were thrown away and rebuilt differently?** If not, it verifies the design's *interpretation* of the requirement rather than the requirement. `design-reviewer` is the only reader positioned for this — it holds both documents and authored neither.
- **The same probe given to `spec-author` as a writing rule**, so the mistake is less likely to be made than to be caught later.
- **Why no structural fix.** Two more ambitious options were worked through and rejected on mechanism, not cost. *Splitting authorship so a clean `spec-author` instance writes the cases blind to design.md* fails because requirements.md already carries Acceptance Criteria — a blind pass can only paraphrase them, since every useful case needs concrete inputs, observable points, and a seam to check at, and all three require knowing the system's shape; `spec-tester` would then read design.md anyway, moving the contamination down a layer rather than removing it. *A fresh (non-blind) instance writing the cases after design* was rejected because a misreading still needs a **checker** to surface, and once the check exists the writer's identity stops mattering — it would buy a second full read for a guarantee the reviewer already provides. **Blindness is a property the writer needs; a checker doesn't need it**, which is why the leverage point is the check.

## 1.19.0 (2026-08-11)

Add the **Test Anchoring Mechanism** and a dedicated `spec-tester` agent. Observed in practice: tests come out thin, and after a refactor or two the suite rots — the expensive part isn't the rot itself but the repair, because a red suite gives no way to separate a real regression from a test that was only ever describing the old structure, so every failure gets investigated and most of that work buys nothing.

The three symptoms share one cause. Tests were written by `spec-implementer` as a side-task, and its success condition is "build passes, design implemented" — a test is a checkbox, not a deliverable, and design.md's `Testing Strategy` was three prose placeholders, so **anything** counted as satisfying it. Worse, the implementer wrote them **looking at the code it had just written**, which produces assertions about the private helper, the call order, the field state gets parked in. Those die at the first refactor by construction. A dedicated test agent alone would not have fixed this: what determines rot speed is **what a test is anchored to**.

- **Only two anchors survive refactoring, and they get different semantics.** design.md's Testing Strategy is now a structured **Test Cases table** (ID / Anchor / Level / Behavior to verify), authored by `spec-author`. An Anchor is either a **requirement number** (a `behavior` case — a refactor must never break it; red means real regression) or a **component's public interface** (an `interface` case — only an interface redesign may invalidate it, and then it is *supposed* to break). The rule that does the work is negative: **a case that can be anchored to neither is not written.** The Behavior column must state an observable outcome ("concurrent push loses no items"), never a mechanism ("push takes the lock before appending") — rot is born in that column, and it costs one table row to prevent there versus a day of repair later.
- **`design-reviewer` reviews the case table** (new aspect §6, with matching checklist items). This is why the table lives in design.md rather than a fourth spec doc: it inherits the multi-round-to-0-issues loop for free, so a requirement with no case becomes a design-stage issue instead of something noticed after shipping. A separate `tests.md` would have needed its own review wiring — and an unreviewed test spec degrades straight back into "short version", just in a different file. Checks: anchor legality, bidirectional coverage (every requirement, every public interface, every Error Handling scenario), behavior-not-mechanism, level fit, no technique prescription. Plus one class only design-time test review can catch: **a requirement that cannot be verified under the current design** (no injection point, no observable state, no clock control) is a *testability defect in the design*, opened against design.md and escalated as an Architecture Decision when the fix is a real trade-off.
- **New `spec-tester` agent (sonnet), dispatched in parallel with `spec-implementer` and blind to its code.** A phase's test tasks form their own group — they write only test files, so they are disjoint from every implementation group by construction and cost nothing against the ≤4 ceiling — and they must sit in the **same phase as the code they cover**, since a test task deferred to a later phase would be written against a finished implementation rather than against the contract. The blindness rule is the mechanism, not etiquette: a writer who cannot see the implementation **cannot** assert its shape. That buys strict TDD's main benefit without serializing the cycle (which would have collided head-on with 1.16.0's parallel grouping). The tester may read the design basis, the requirements, the steering docs, and anything that existed before this cycle; if the basis doesn't say enough to write the test, that is a **blocker report**, not a licence to peek — and a valuable one, since it means the basis is under-specified.
- **Mode 1 red is the designed output.** The tester is told never to soften an assertion, skip a test, or go look up "what it actually returns" to reach green — a test adjusted into passing certifies whatever the code happens to do. The main agent joins the two dispatches and classifies each failure: implementation wrong → implementer; test wrong about the contract → tester; **basis doesn't settle it → `spec-author`**. That third case is the quiet win — two agents reading the same design basis and disagreeing is direct evidence the basis is ambiguous, a signal that simply did not exist when one agent wrote both sides.
- **Refactor triage replaces investigation.** Red is classified by anchor, mechanically: requirement → fix the code, test unchanged; an interface *this change redesigned* → rewrite from the new design or delete, never patch back to green (patching reintroduces the coupling); untraceable → delete, repairing it buys nothing. And `/update-spec` now settles it **at the moment the design changes** — a revision that removes or redesigns an interface strikes its dependent cases from the table in the same edit and marks their test tasks `[~]` / `[-]`, reusing tasks.md's existing markers rather than adding machinery. "Which tests should die" becomes a recorded design decision instead of a guess made months later by whoever hits the red.
- **`spec-implementer` is told explicitly that tests are no longer its job** — a positive rule without its negative boundary gets both agents writing tests into one worktree. It doesn't author tests, doesn't touch test files, and doesn't "fix" a failing one; it reports the disagreement, because an implementer that edits the test has destroyed the independence that made the test worth having. Self-verification and the build check are unchanged. `implementation-reviewer` gains the test suite as review scope, routes test issues to `spec-tester` rather than the implementer, and now grades **a test asserting internal structure as a Smell even when it is green**.
- **Quick Fix Mode runs a lightweight version**: no case table, no separate tester — the plan's change list names the tests to add or change and the implementer writes them, with the anchoring discipline intact. The ceremony is what gets dropped, which is the point of the mode.

## 1.18.2 (2026-08-11)

Fix a rule that was documented as structurally enforced and was in fact not enforced at all: **`disallowedTools: advisor` never kept subagents off the advisor.** Reported from use — with advisor mode on, subagents still consult it. The transcripts confirm it at scale: across this plugin's own agents, **139 subagent runs made 185 `advisor` calls, and every one of the seven agent types is represented** (`spec-author`, `spec-implementer`, both reviewers, both verifiers, `spec-researcher`). Outcomes were mixed — 58 calls errored because advisor mode happened to be off in that session, but 124 got a real answer back (40 `advisor_result`, 84 redacted). The restriction wasn't degrading gracefully; it was absent.

The mechanism explains why nobody noticed. An advisor call is emitted as a **`server_tool_use` block** — the advisor is attached to the request server-side when advisor mode is on and never passes through the *client* tool registry that `disallowedTools` filters. The agent registry dutifully reports these agents as "all tools except advisor", which is true of the registry and false of what the model can call. The same fact rules out the fallback used for other unenforceable rules: a `PreToolUse` hook fires on client tool calls, and a server tool never round-trips to the client, so **there is no interception point** — unlike 1.18.1's `run_in_background`, prose is not the first line of defense here, it is the only one.

- **An explicit "Never call the advisor" section in all seven agent definitions.** It does three things a bare prohibition doesn't: names the harness's injected advisor guidance, states that it is addressed to the *main agent* and is overridden here, and says outright that the frontmatter doesn't bind so this instruction is the only thing holding the line. The naming matters — the injected guidance actively instructs its reader to consult before substantive work, so a prohibition that ignores it leaves the agent weighing an explicit instruction against silence. Each agent also gets the **substitute** appropriate to its role, because wanting a stronger opinion is the escalation signal: a blocker report (`spec-implementer`, `spec-author`), an Architecture Decision handed up in the issue list (the reviewers), an honest failed/uncertain item (the verifiers), an unsettled evaluation (`spec-researcher`). Reinforced as a Key Principle wherever the file carries such a list, and as a shared reviewer discipline in `review-protocol.md` (which both reviewers read at startup).
- **The frontmatter stays, the claim about it doesn't.** `disallowedTools: advisor` is kept on all seven — it records intent and would take effect if the tool ever became client-side — but every doc that cited it as the enforcement now says plainly that it does not bind (`advisor-gate-guide.md`, SKILL.md's Advisor Gate section and reference table, `review-protocol.md`). A silent non-binding restriction plus a registry claiming "except advisor" is exactly what let this run for five releases.
- **The ban propagates to what the executors themselves spawn.** The same transcript sweep found built-in `Explore` / `general-purpose` agents calling the advisor too — and those can't be edited at all, so the spawn prompt is the only lever. The main agent and both reviewers were already told to add that line; `spec-author` and `spec-implementer` were not, even though their tier-pinning guidance actively tells them to fan searches out. Both now carry it, closing the same defect one level down.
- **The main agent's side**: never tell a subagent to "check with the advisor", and treat an advisor consult surfacing in a subagent's report as a dispatch defect to correct rather than a result to use.
- **Stated honestly in the docs**: prose biases the outcome, it does not guarantee it. If subagent advisor calls persist, the remaining fix is upstream in the harness — there is no further mechanism available inside this plugin.

## 1.18.1 (2026-08-09)

Tell the executors a fact about their own execution they cannot observe from the inside: **a subagent cannot be woken.** Observed repeatedly — `spec-implementer` starts a build or test with `run_in_background` and ends its turn expecting a completion notification, then reports on work whose outcome it never saw.

The main agent may background work safely: the harness wakes it when the task finishes. A subagent has no equivalent — it is a transcript, not a live process, so ending its turn stops it completely and the *only* thing that can restart it is the main agent messaging it. The backgrounded command really does run and really does finish; nothing then exists to tell the subagent. Nothing in the tool surface signals that the two cases differ, which is exactly why it recurs: the tool works, and "kick it off and wait for the notification" is a heavily-reinforced pattern. This is a **knowledge gap, not a discipline problem** — so the fix states the mechanism and the alternative rather than issuing a bare prohibition (a denial without a substitute just produces `nohup`-shaped workarounds).

Rules given to both executors: **foreground every build, test, and long command and wait for it**; **narrow what is too slow** (one target, one test file, the single project touched) rather than backgrounding it; **escalate what genuinely can't be narrowed** as a blocker report — the main agent has the wake-up mechanism the executor lacks. Also: never report a build or test as passing on the basis that it was started. Threaded through `spec-implementer.md` (build check + a dedicated section + a Key Principle), `spec-author.md` (matters most during 1.18.0's approach-settlement repros), and SKILL.md's executor-contract paragraph, which additionally tells the main agent its side: scope dispatches so the executor's runs are bounded, or run the long command yourself and hand the result in.

## 1.18.0 (2026-08-09)

Add the **fix escalation ladder** — *who settles a fix*, as a third axis beside "how much goal per dispatch" (1.15.0) and "how many executors" (1.16.0). Observed in practice: the initial spec implementation and the early review rounds go fine, but once real testing surfaces bugs — especially ones needing a root cause found, an architectural change, or a call between several fix directions — `spec-implementer` (sonnet, built to implement a settled basis faithfully) is the wrong tier to be deciding anything. Asking the cheap tier to do the expensive part is the generator/arbiter inversion this skill exists to prevent, so escalation is now keyed on observable triggers rather than left to whoever is holding the issue.

- **Five rungs, one ladder** (folded into "Dispatch Granularity" rather than added as a competing doctrine): **(1)** mechanical item with an explicit landing point → `spec-implementer` Mode 2 direct, unchanged default; **(2)** path unclear but scope local → stepwise dispatch, same session (1.15.0, unchanged); **(3)** **root cause unknown / several viable directions / touches framework or a cross-component contract → `spec-author` (premium tier) investigates and settles the approach into the design basis**, and the implementer implements the settled approach; **(4)** the judgment layer already tried and missed → **the main agent diagnoses personally**, then dispatches `spec-author` to record the conclusion; **(5)** Round 5 with new Critical/High → convergence fuse → the user (unchanged).
- **Rung 4's triggers are per-problem, unlike the fuse's per-loop one** — any one suffices: a rung-3 settlement that didn't hold (same issue or an obvious mutation re-opens), two cumulative failed fix attempts on one problem (the 1.15.0 thrashing definition, now accumulating per issue rather than per dispatch), or rounds accumulating without the Critical/High count trending down (watch from Round 3, evidence already in review-log §1 — no new counter competing with the fuse). "The main agent diagnoses personally" means going to the **primary evidence** — the actual code, the failing output, the cross-round pattern — instead of working from the reviewer's summary; it still never writes the fix (Principle #11 now says explicitly that it forbids *writing code*, never *thinking*). This also sharpens the fuse: when Round 5 trips, the top judgment layer has already been down there and failed, which is what makes a structural verdict a conclusion rather than a shrug.
- **Blocker-report routing supersedes 1.15.0's fixed response** — that release said receiving a blocker report *is* the thrashing trigger, "respond by going stepwise". Now a blocker report routes to **classification**: the main agent reads it and picks rung 2 (path unclear, local) or rung 3 (root-cause / architectural). `spec-implementer` is told not to pre-judge that routing — softening a root-cause problem into "just tell me which way to go" keeps diagnosis on the wrong tier.
- **Approach settlement is a named dispatch shape inside `spec-author` Mode 2**, not a new mode (Mode 2 was already "issue-driven revision of the design basis"): investigate against primary evidence, settle **one** approach with its trade-off stated (a menu hands the decision back, which is what the dispatch delegated away; a genuine user-level call is escalated explicitly instead), write it into the basis as ordinary design prose the implementer can act on without reading the review log, and flag interface impact in the report. Boundary reinforced: reading code and running repros is diagnosis, editing a source file is not — however obvious the fix looks once found.
- **Does a settled approach need its own design review?** Named rather than silently exempted: an approach that **stays within the existing architecture** rides the implementation loop (the next round reviews the fix against the revised basis); one that **changes structure or a public/cross-component interface** is a real design change and takes the existing path (`/update-spec`'s design-review loop, or a design-reviewer round on the revised plan). ## 1.15.0 (2026-07-18)

Add **Dispatch Granularity** — how much goal the main agent hands an executor per dispatch — plus the executor-side escalation contract. ## 1.14.0 (2026-07-17)

Make the backlog **safe for concurrent sessions**, on two independent axes. 1.11.0 gave deferred discoveries a durable home but assumed one writer: item ids came from a counter, and a picked-up item carried no claim. Both assumptions break the moment two branches / worktrees / terminals touch the backlog — and they break in different ways, so they get different fixes.

- **Ids are random hashes, not sequential numbers** — `bl-{NNNN}` → `bl-{hash}` (6 hex chars). The real defect was never the *format*: it was that a counter forces every writer to read global state first ("scan root + archive for the highest existing id"), so two sessions that scan concurrently both see `bl-0008` and both write `bl-0009`. **The id generation was the race**; a random id needs no coordination, so there is nothing to race on. That read-the-highest-id scan is deleted outright, replaced by a cheap existence re-check (regenerate on the freak collision).
- **The generator is pinned, and that pin is the whole change** — `[guid]::NewGuid().ToString('N').Substring(0,6)`, stated as mandatory in both `backlog-guide.md` and SKILL.md. A doc that merely said "use a hash" would be actively worse than the counter: the main agent writes items inline, and an LLM asked for six "random" hex characters is not an RNG — it repeats and clusters, so ids would collide exactly as before, except now silently and unfixably. Random GUID-slice over content-hash deliberately: content-hash's only extra gift is dedup of identical items, which nobody needed, at the cost of input assembly and another layer of model judgment.
- **Chronology moves to `date`** — ids no longer imply sequence, and nothing is lost: `date` was already in every index line and every item's frontmatter. `/backlog` never parsed ids numerically, so it needed no change.
- **Picked-up items are claim-marked** — a separate race the ids don't touch: unique ids stop two sessions *recording* the same id, not two sessions *working* the same item. On pick-up, **before the work starts**, the item gets `status: in-progress` + `picked_up: DATE (branch: X) — what's being done`, and the index line flips to `[~]` carrying the same claim inline. Each of the three fields earns its place: date (is this claim minutes old or a month stale?), branch (go look at the work), one sentence (does it overlap with what I was about to do?). Mark-first-work-second — a claim written after the work starts protects nothing during the window where the collision happens.
- **A `[~]` item is never silently taken over or silently skipped** — the finder reports the claim to the user and lets them decide (pick something else / take over an abandoned session / coordinate). **No expiry rule, on purpose**: "older than N days = stale, take it freely" has no defensible N, and a two-week claim can be an active long-running branch while a two-day one is dead. Whether a claim is live is knowledge that exists outside the repo, so it's a genuine user call with no safe default — the one place in this flow where asking beats guessing. `/backlog list`'s existing stale-item flagging already covers the cleanup need without guessing.

## 1.13.0 (2026-07-12)

Extend the advisor gate with a **second application — co-arbitrating reviewer output**. The 1.12.0 gate fired before the main agent interrupted the *user*; this adds the advisor as a second pair of eyes before the main agent commits a consequential judgment of a *subagent's returned output*. Motivation: the generator/arbiter split already has the main agent challenge the reviewer every round, but the *outcome* of that challenge — what gets fixed vs dropped — is still the premium main agent's solo call, and that solo call is exactly where a wrong dismissal or a false convergence does the most damage.

The consult happens *before* the round's single challenge so it shapes it. No new section. Principle #13 renamed "Consult the Advisor Before a Consequential Call"; the mechanism is threaded across SKILL.md, review-protocol.md, advisor-gate-guide.md (new §8), and review-log-guide.md.

## 1.12.0 (2026-07-12)

Add the **Advisor Gate**: before the main agent stops to ask the user any decision, it consults the **advisor** first (a stronger reviewer model that sees the full transcript). Motivation: on a premium session model the main agent interrupts the user far more often than the work warrants — many stops are "which of these two technically-equivalent paths" calls a competent engineer would just decide, and each one costs the user a context-switch (and, on an expensive tier, the reluctance to decide is itself expensive). - **Triage, not takeover** — the advisor settles decisions with a defensible technical answer (codebase consistency, standard idiom, disambiguation); it passes through genuine preference/product/business-priority calls, irreversible / high-blast-radius choices (schema migration, data loss, external contract, security posture), and anything it flags as uncertain. Steering promotion passes through as a user-confirmed guardrail call (Principle #7); Medium/Low keep defer-and-batch; mode up/downgrade stays the main agent's own informed routing call.
- **Recorded + surfaced (the safety valve)** — an advisor-resolved decision lands in `review-log.md` §2 tagged `[advisor-resolved · pending your review]` with `Rationale (advisor, DATE)` and a new §1 Status `advisor-resolved` (Quick Fix uses the plan file's embedded log). ## 1.7.6 (2026-07-01)

Fix the briefing checkpoint hook false-blocking the **compliant** flow — brief turn-final → user reply → ExitPlanMode — whenever a routine plan-mode marker happened to sit between the reply and the exit. A regression from the 1.7.1 anchor.

- **Root cause**: 1.7.1 anchored the check to "the current plan session" by treating a bare `{type:"permission-mode",permissionMode:"plan"}` marker as the (re-)entry boundary, assuming it only appears on a manual shift+tab re-entry. But Claude Code writes that **same** bare marker at essentially **every** plan-mode turn boundary (verified against live transcripts: it recurs while plan mode is already active, clustered with `last-prompt` / `mode` bookkeeping). So whenever such a routine marker fell between the user's reply and ExitPlanMode, the single backward walk hit the marker first and DENIED — false-blocking the exact flow the hook exists to allow. It bit reliably because the spec flow almost always does *something* after the user's approval (applies the tweak, updates the plan, loads the deferred ExitPlanMode) before exiting, re-emitting the marker.
- **Fix — split the single walk into two passes**. Pass 1 runs a small state machine to find where the current plan session started, using **reliable** signals only. A session *opens* on an `EnterPlanMode` tool call, a genuine `→plan` transition read from a **real user message's own `permissionMode` field** (a human action, so it can't be routine bookkeeping — the dependable signal for a manual re-entry, which carries no `EnterPlanMode` call), or a bare `permission-mode:plan` marker seen **while not already in plan**. A session *closes* on an **approved** ExitPlanMode (Claude Code delivers a "…approved your plan…" tool_result; a *denied* exit carries our own deny reason instead, so it does **not** close and recovery never deadlocks) or a real user message with a non-plan `permissionMode`. A bare `permission-mode:plan` marker seen **while already in plan is ignored** — that is the routine turn-boundary bookkeeping that caused the false-block. Pass 2 walks back from ExitPlanMode only to that boundary.
- **Kept intact on purpose**: a briefing **crammed into the same turn** as ExitPlanMode still DENIES — that message carries a tool_use so it is skipped as mechanical and the walk denies at the session boundary; a crammed mid-turn briefing may not even render, so blocking it is correct. Manual re-entry after a restart is still anchored via the reliable transition signal. Modeling session *close* (not just *open*) is what stops a later unbriefed shift+tab re-entry from leaking to the previous session's approval reply. **Residual** (accepted, all fail-open — err toward allow, never a false-block): the plan-entry scrolled off via compaction (no session identified → allow); a restart lands while already in plan with no intervening non-plan message (re-entry not detectable); and a shift+tab out-of-plan-then-back-in via bare markers with no typed message in between (bare non-plan markers are deliberately not treated as a session close, since doing so would let routine bookkeeping markers close a live session and re-introduce the very false-block this release removes). All three are consistent with the hook's fail-open discipline and strictly better than the false-block they replace.
- **Tests**: `briefing-checkpoint.test.js` grows 12 → 20. New cases pin: the reported false-block (routine marker between reply and exit → allow — **would have denied on the old hook**); manual re-entry detected via the user-message `permissionMode` transition (deny without a fresh briefing, allow with one); the cross-session leak (approved exit → unbriefed bare-marker re-entry → deny, vs briefed → allow); that a *denied* exit does not close the session so recovery still allows; and fail-open when no plan session is identifiable. `hooks.json` description updated in sync.

- **hook changed to protect "every ExitPlanMode"** (removing 1.6.6's design-reviewer cycle-scoping): reason — a briefing that lowers cognitive load benefits any plan, and the hook's fail-open won't break plan mode, so no narrowing. Benefits: the create-spec/update-spec plan-exit won't be missed (its design-reviewer Mode A is optional, and scoping would misjudge it); plain plan mode is protected too (one extra summary, harmless). The hook is therefore **greatly simplified** — leaving only the "is the entry before ExitPlanMode a user reply" skip judgment + isSidechain/isMeta filtering + fail-open, removing the whole design-reviewer detection and cycle-start delimitation.
- Knock-on: design-reviewer's scope adds /update-spec, review-protocol's convergence reminder becomes mode-aware, and briefing-guide's trigger table + cognitive-load principle + layer 3 of the three-layer architecture are in sync.

## 1.6.6 (2026-06-15)

The ExitPlanMode briefing checkpoint changed from a **prompt hook to a deterministic command hook**, curing the 1.6.2–1.6.5 deadlock for good. (Note: this version number previously had a short-lived "remove the hook" commit that was pushed and then reverted via force-push, not retained on the remote; this 1.6.6 is the official release. If a stale 1.6.6 directory remains in the local plugin cache, it must be cleared and re-pulled to get this version's content.)

- **Root cause**: the prompt hook's judge is an LLM that can't see the conversation history. Even when instructed to "always allow", it still conservatively blocks ExitPlanMode because it "can't confirm whether the briefing was delivered" — blocking even when the briefing was correctly delivered and the user confirmed, causing a deadlock where the agent can't propose a plan (observed blocking twice in a row in practice). An LLM will override the prompt instruction itself, and can't serve as a reliable gate.
- **Solution**: switch to a Node command hook (`hooks/briefing-checkpoint.js`, deterministic code, not an LLM). Reads the transcript to judge "is the entry before ExitPlanMode a real user reply" — the turn-final briefing discipline guarantees a legitimate flow is always immediately preceded by a user reply; a skip is always assistant / tool_result. Yes → allow; skip → block and return a short reminder.
- **Scope narrowing (no hijacking of normal plan mode)**: although the hook is mounted on all ExitPlanMode, it only enforces **when "this plan cycle has run design-reviewer"** (= the spec-driven Quick Fix flow). The cycle start is delimited by **the most recent entry into plan mode** (`permission-mode:plan` / `mode:plan` / `EnterPlanMode` tool_use), and design-reviewer only counts if it comes after that start — calls between rounds (e.g. Spec Mode `/create-spec`, which also runs design-reviewer but not in plan mode) won't be miscounted. **If no cycle start is found, allow** (do not fall back to "the previous ExitPlanMode" as the boundary — that's the previous round's end and would fold the gap in, producing a false positive). Plain plan mode has no design-reviewer → always allow, so installing the plugin won't affect built-in plan mode.
- **No deadlock**: after the briefing + user reply, the preceding entry is a user message → allow; and **fail-open** — unreadable transcript / parse failure / not a Quick Fix cycle all allow, blocking only on "a confirmed skip inside a spec-driven cycle".
- **Detection details**: a subagent call appears in the transcript as an `Agent`/`Task` tool_use + `input.subagent_type`; the hook detects design-reviewer from this. It also filters out `isSidechain` (subagent-internal messages, otherwise false-deny) and `isMeta` (injected local-command / reminder, otherwise false-allow). A real human reply is `type:user` with string content.
- **Markers verified in practice** (against real transcripts): user manually shift+tabs into plan mode → `{type:"permission-mode", permissionMode:"plan"}`; agent enters via tool → `EnterPlanMode` tool_use. Both cycle-start paths are detectable, so "user manually enters plan mode first" won't cause a miss. (The `mode` field is always `"normal"` in a bypassPermissions session; the plan state lives in `permissionMode`.)
- **Cross-platform + stateless**: pure Node (shipped with Claude Code), works on Windows/Linux/Mac; only reads stdin + transcript (read-only), writes no file anywhere (including the project folder). The command uses `node "${CLAUDE_PLUGIN_ROOT}/hooks/briefing-checkpoint.js"`.
- briefing-guide's "three-layer reminder architecture" layer 3 is restated as a command hook; README Hooks section in sync.
