# Visual Design (UI features)

This file is the one home for the visual-design rules; the flow steps in SKILL.md and the other files point here. Read it when a `/create-spec` or `/update-spec` planning phase involves a feature with UI, before drawing, redrawing, installing the viewer or publishing a mirror, and when implementing or reviewing a change whose design.md carries a `**Visual design:**` pointer line.

> **`design` below is shorthand** for the design command stated in SKILL.md "File Structure" (`node "<plugin root>/scripts/design.mjs"`). Use the absolute path SKILL.md gives, exactly; `${CLAUDE_PLUGIN_ROOT}` is not set in the shell, so never type the variable into a Bash call. Subcommands: `list`, `install-viewer --from <dir> --source <url>`, `set-mirror <feature> <url>`, `view [<feature>] [--port <n>] [--no-open]`.

A feature with UI has its screens drawn as a Claude Design canvas kept in the repo at `.spec/design/<feature>/` (SKILL.md "File Structure"). The files are the design: every drawing and revision is an agent editing them, they are committed like a spec, and `/design-view` renders them offline. Spec Mode only; Quick Fix draws none, and a quick fix on a feature that has a design reads it as reference.

- **Availability.** A new design is started only when `quickstart` with intent `design` offers the Design type; otherwise the feature has no visual design and no pointer line, and the flow continues. An existing design can be redrawn without the type. When there is no format source at all (no installed `reference/` and no Design type to read), the brief passes the existing boards and `canvas.json` as the format reference, and the main agent tells the user only what `design list` and the `quickstart` result actually rule out: with `viewer: not installed`, offline viewing waits until a viewer is installed from a canvas the user owns; without the Design type, no new mirror can be created (republishing to an existing mirror the user can write still works).
- **Installing the viewer** (once per project, when `design list` says it is not installed, and always before a drawing or a publish if it is missing). Take any Design canvas the user owns, or create a throwaway one with `Artifact` publish from the `type_url` that `quickstart` with intent `design` returns, a title and no files (then tell the user in one line that it was created for this and offer to delete it; delete it only on their request). `Artifact list` with `scope: "files"` on it; `Artifact read` with `paths` = `index.html` and every listed `artifact-type/` path, into the default `out_dir`; only when every path downloaded, `design install-viewer --from <that folder> --source <canvas url>`. To switch runtime builds, run the same steps from a canvas on the other build. The runtime is never shipped in this plugin and is ignored by its own `.gitignore`, so each clone installs it once.
- **Drawing.** The main agent settles the design system with the user and prepares the authoring format. When `design list` shows `format installed`, the brief passes `<viewer path>/artifact-type/reference/`. Otherwise the main agent reads the type (`Artifact read` with the `type_url`) and the pages it names (`Artifact read` with the `url` of a canvas the user owns, the throwaway canvas or a mirror, and each page's `path`), and saves them into one scratchpad file whose path the brief passes. Either way the brief also carries the chosen design system's README. `spec-author` reads only the files the brief names, never calls the Artifact tool, writes into `.spec/design/<feature>/`, and is resumed for each round of user feedback. Drawing happens in the `/create-spec` or `/update-spec` planning phase, before the Plan Briefing, which points at `/design-view <feature>`; in `/update-spec`, only where the agreed change needs drawing.
- **Snapshot and rejection.** Before the flow's first drawing dispatch (once per flow, not per feedback round), the main agent copies `.spec/design/<feature>/` into its scratchpad, or records that it is absent. If the user rejects the direction at the briefing, restore that snapshot exactly (replace the directory with the copy, so files the rejected drawing created go too), or delete the directory when the record says absent; git is not involved, because the directory may hold uncommitted work that predates the flow. If the snapshot is missing (a new session, say), never delete or restore: ask the user.
- **The design.md pointer line** `**Visual design:** .spec/design/<feature>/` is written when `.spec/design/<feature>/project/canvas.json` exists at the time design.md is written: by `spec-author` with design.md in `/create-spec` step 10, and in `/update-spec` step 6, which adds it when the canvas exists and design.md has no pointer line, even when the agreed change does not otherwise touch design.md. A design that a rejection restored to absent gets no pointer line. design.md carries the pointer and no description of the visuals; requirements.md acceptance criteria may name a board by its title.
- **The contract scope.** A board is the contract only for what the agreed change alters, as pinned by requirements.md and the change's tasks, for layout, copy and states. Every element the change does not alter keeps the shipped code, even on a screen the change builds, so a board still showing an older version of an untouched control never reverts it. Implementers build the altered elements to match the boards and leave the rest as shipped; `spec-tester` may read the boards but anchors cases as before; the two reviewers check the altered elements against the boards and judge the rest against the shipped code.
- **Design-review fixes.** A design-review issue on the boards is fixed by `spec-author` Mode 2 like any other issue: it edits only the boards the issue names and lists each in its completion report. The final Spec Briefing names every board changed after the Plan Briefing and points at `/design-view <feature>`.
- **Intent layer.** Like design.md, the design is intent: after ship the code is the truth, and a board is redrawn only by a change that alters those visuals, never reconciled to the code. The unaltered parts of a board may therefore be stale.
- **Publishing (optional, on the user's request).** When `design list` reports `viewer: not installed`, install the viewer first (per "Installing the viewer"), so `set-mirror` can record the mirror as soon as it exists and no mirror is left unrecorded. When `list` shows no mirror for the feature, create one with `Artifact` publish from the `type_url` that `quickstart` with intent `design` returns (a title, no files, `auto_open: "after_first_write"`) and record it with `design set-mirror <feature> <url>`. Then, and on every republish, `Artifact read` the mirror (a publish to an artifact not read in this session is refused); if the read shows it is gone or not writable by this user, create a new mirror as above and tell the user. `Artifact list` with `scope: "files"` on it, and publish with `url`, `root` = `.spec/design/<feature>`, and `files` mapping every file under it to its own path, plus `null` for each listed `project/` path that no longer exists locally. The mirror is a snapshot for viewing and sharing: it is never edited there, nothing is read back from it, and it is never the contract.
